# Claude Code Academy

An independent, self-paced course web app for learning Claude Code. Google + email/password
auth, 9 modules (7 + 2.5 + capstone) each with a lesson, quiz, and hands-on practicum, and a
downloadable PDF certificate of completion once every module is verified.

Not affiliated with or endorsed by Anthropic — say so anywhere the course is described publicly.

## Stack

- **Next.js 16** (App Router, TypeScript, Turbopack) — see `AGENTS.md` (auto-generated by Next.js)
  before assuming anything about Next.js APIs matches older training data. Concretely, in this
  install: `shadcn` generates **Base UI**-based components (`@base-ui/react`), not Radix — polymorphism
  uses a `render` prop, not `asChild` (see **Gotchas** below). Middleware has been renamed to
  **Proxy** (`proxy.ts` at the root, exported function named `proxy`), not `middleware.ts`.
- **Tailwind CSS v4** — theme tokens live in `src/app/globals.css` under `:root` / `.dark` (no
  `tailwind.config.js`). Palette is a custom warm clay/cream design, not Anthropic's actual
  brand colors.
- **shadcn/ui** (Base UI-based, style `base-nova`) — components in `src/components/ui/`.
- **Supabase** — Postgres + Auth (Google OAuth and email/password) + row-level security. Schema
  lives in `supabase/schema.sql`.
- **@react-pdf/renderer** — generates the certificate PDF on demand in `src/app/api/certificate/route.ts`
  (Node runtime, not edge).

## Architecture

- `src/lib/content/modules/*.ts` — all course content (lessons, quiz questions, practicum
  scenario + validation rules) as plain data, one file per module, aggregated in
  `src/lib/content/modules/index.ts`. **Adding a module = adding a file here** and wiring it into
  the index; no other code changes needed. See `src/lib/content/types.ts` for the shape.
- `src/lib/content/validation.ts` — declarative practicum-check evaluator (`includesAny`,
  `includesAll`, `regex`, `minLength`, `minLines`). Checks run identically on the client (instant
  feedback) and the server (source of truth) since they're pure data + a pure function — never
  swap this for arbitrary closures, it would break that symmetry.
- `src/lib/supabase/{client,server,proxy}.ts` — the three Supabase client flavors per the
  official `@supabase/ssr` pattern (browser / server component / proxy).
- `src/lib/progress.ts` — reads `module_progress` rows and derives completion. A module counts as
  complete only when **both** `quiz_passed` and `practicum_verified` are true; the course counts as
  complete only when every module in `courseModules` is complete.
- `src/app/modules/actions.ts` — the only place quiz/practicum submissions are graded and written
  to the DB (server actions, called directly from the client components in
  `src/components/{quiz,practicum}-form.tsx`). Grading always re-runs server-side even though the
  client also has the answer key, so a tampered client can't self-certify.
- `src/app/api/certificate/route.ts` — gates on `isCourseComplete`, issues a `certificates` row
  once (stable certificate number + issue date), then re-renders the PDF from that row on every
  request rather than storing the binary — simplest correct approach, no storage bucket needed.
- Auth pages (`src/app/(auth)/...`) use **Server Actions** (`src/app/(auth)/actions.ts`), not
  client-side Supabase calls, so cookies get set correctly during sign-in/sign-up/OAuth.
- `public/starters/*.zip` — downloadable practice projects a learner can point Claude Code at for
  a practicum instead of hunting for their own repo. Listed in `src/lib/content/starters.ts` and
  rendered by `src/components/starter-projects.tsx` on every module's Practicum tab (not
  per-module — which starter fits depends on the exercise, not the module, see each starter's
  `goodFor` field). **To add or update a starter**: build it in a scratch dir, `npm install` +
  actually run its tests/server there to confirm it works, strip `node_modules` before zipping
  (keep `package-lock.json`), then drop the zip in `public/starters/` and add an entry to
  `starters.ts`. Never hand-edit a zip in place — rebuild it from source so the working copy and
  the shipped archive can't drift.
- `lessonSections[].examples?: CodeExample[]` (`src/lib/content/types.ts`) — optional real code
  blocks (a filename `label` + literal `code`) rendered by `src/components/code-block.tsx` after
  a section's prose. Used for things like exact slash-command files and hook config, where prose
  alone was too vague to actually act on (see Module 4). Examples render after all of a section's
  `body` paragraphs, not interleaved — if you need prose after a code block, split into a second
  section rather than reordering the array (an empty `heading` renders a visible blank `<h2>`,
  so give every section a real one).

## Gotchas learned while building this

- **Base UI `render` prop, not `asChild`.** `<Button asChild><Link .../></Button>` compiles under
  older shadcn muscle memory but fails to typecheck here. Use
  `<Button render={<Link href="/x" />}>text</Button>`. When the render target isn't a real
  `<button>` (a `Link`/`<a>`), also pass `nativeButton={false}` or Base UI logs a dev warning.
- **`DropdownMenuLabel` needs a `DropdownMenuGroup` wrapper.** It renders Base UI's
  `Menu.GroupLabel`, which throws "MenuGroupContext is missing" at runtime (not a typecheck
  error — it crashes the page on click) unless it's inside a `<DropdownMenuGroup>`. This bit us in
  `src/components/navbar.tsx`'s account menu. Also: a `DropdownMenuItem` rendered as a real
  `<button>` (e.g. the sign-out form button) needs `nativeButton` set explicitly — `MenuItem`
  defaults it to `false`, the opposite of `Button`'s default of `true`.
- **RadioGroup must be controlled from the first render.** Passing `value={undefined}` until
  something is selected trips Base UI's uncontrolled→controlled warning. Default to `""`, not
  `undefined` (see `src/components/quiz-form.tsx`).
- **Next.js private folders.** A route folder prefixed with `_` (e.g. `src/app/_foo`) is invisible
  to the router by convention — don't use that prefix for a real route.
- **`proxy.ts` / session refresh is unverified in this dev sandbox.** Despite following the
  documented Next 16 + `@supabase/ssr` pattern exactly (and it compiling correctly — confirmed by
  inspecting the emitted chunk), requests to a local `next dev` in this container never actually
  invoked the proxy function (no header/log side effect fired, with both Turbopack and webpack,
  under both the `middleware.ts` and `proxy.ts` filenames). This did **not** block shipping because
  every protected page (`/dashboard`, `/modules/[slug]`, `/certificate`) already independently
  checks `auth.getUser()` and redirects server-side — access control does not depend on the proxy
  running. The proxy's only job is proactively refreshing the session cookie so a long-idle tab's
  next server-rendered page load doesn't show a stale session; Supabase's browser client also
  auto-refreshes in the background once JS loads. **Before relying on this further**, verify on
  your own machine and on Vercel that `proxy.ts` actually fires (e.g. add a temporary
  `res.headers.set(...)` and check with `curl -I`) — if it does, this note can be deleted.

## Environment variables

Copy `.env.local.example` to `.env.local`. Required: `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SITE_URL`. See **First-time project setup** below for
where these come from.

## First-time project setup (Supabase + Google OAuth)

1. Create a project at [supabase.com](https://supabase.com).
2. In the SQL editor, run `supabase/schema.sql` once.
3. Settings → API: copy the Project URL and `anon public` key into `.env.local`.
4. Authentication → Providers → Email: on by default; confirm "Confirm email" matches whether you
   want email verification before first login (the app assumes confirmation is required — see
   `src/app/(auth)/signup/check-email/page.tsx`).
5. Authentication → Providers → Google: enable it, and add a Google Cloud OAuth client
   (console.cloud.google.com → APIs & Services → Credentials → OAuth client ID → Web application).
   - Authorized redirect URI: `https://<your-project-ref>.supabase.co/auth/v1/callback`
   - Paste the resulting Client ID/Secret into Supabase's Google provider config.
6. Authentication → URL Configuration: set the Site URL and add a Redirect URL for
   `<your-site>/auth/callback` (both the production domain and `http://localhost:3000` while
   developing).

## Ship-it workflow

Follow this in order for every change that goes to production. Don't skip steps to save time —
this is a small app but it handles auth and a paid-for domain; a broken deploy is more expensive
than five extra minutes.

### 1. Before writing code
- Confirm the change's scope in one sentence. If it touches auth, the DB schema, or the
  certificate/progress-gating logic, write down the exact before/after behavior before editing.
- If it adds or changes a `supabase/schema.sql` table/policy, plan the migration as an additive
  SQL snippet (new file or a clearly-marked new section), not a silent rewrite of the existing
  schema — the existing file is the source of truth for a project that may already have real rows.

### 2. While coding
- New module → new file in `src/lib/content/modules/`, wired into `index.ts`. Don't hand-edit
  `courseModules` anywhere else.
- Any new interactive shadcn primitive → check whether it needs `render`/`nativeButton` per the
  Gotchas section before assuming Radix-era APIs.
- Keep practicum checks declarative (`CheckRule`), not closures, so client/server grading stays
  identical.

### 3. Before every commit
Run all four, in order, and fix failures before committing — don't commit past a red step:
```bash
npx tsc --noEmit    # (run after at least one `npm run dev`/`build` so Next's generated types exist)
npm run lint
npm run build
```
- Manually smoke-test in the browser at both a mobile width (375px) and desktop: landing page,
  sign up, log in, one module's lesson/quiz/practicum tabs, dashboard. This app is explicitly
  supposed to be mobile-optimized — a regression here is a real bug, not a nitpick.
- If the change touches quiz grading or practicum validation, submit at least one intentionally
  wrong answer and one intentionally correct one and confirm both are graded as expected — the
  server action is the source of truth, so test through the real UI, not just by reading the code.

### 4. Commit and push
- Commit message describes *why*, not just *what* (this repo's own convention — check
  `git log` for tone/style before writing one if this is a later session).
- Push to a feature branch and open a PR unless the user has said direct-to-main is fine for this
  repo's current stage.

### 5. Deploy (Vercel)
1. `vercel link` (first time) or push to the branch Vercel is already watching.
2. In the Vercel project's Environment Variables, set `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `NEXT_PUBLIC_SITE_URL=https://claude.cdlav.us` for
   Production (and a separate `NEXT_PUBLIC_SITE_URL` per Preview URL if you want OAuth to work on
   preview deployments too — otherwise Google/email redirects will point at production from a
   preview build).
3. In Supabase → Authentication → URL Configuration, make sure the production redirect URL
   (`https://claude.cdlav.us/auth/callback`) is present — a deploy with a missing redirect URL
   will build fine and then fail silently at the OAuth callback step, so check this **before**
   telling anyone the deploy is done.
4. Add `claude.cdlav.us` as a domain on the Vercel project. Vercel will show the exact DNS record
   to add (typically a CNAME to `cname.vercel-dns.com`) — add it at whatever host manages the
   `cdlav.us` DNS, then wait for Vercel to confirm verification before assuming it's live.
5. After the domain is live, hit it once yourself: load the homepage, sign up with a throwaway
   email, confirm the confirmation email arrives and the callback logs you in. An auth flow that
   only gets tested against `localhost` is not tested.

### 6. Rollback
- Vercel keeps every deploy; "Promote to Production" on the last-known-good deployment is faster
  and safer than a revert commit under time pressure. Revert the commit afterward so `main` matches
  what's live.
- A bad `supabase/schema.sql` change is not a Vercel rollback problem — fix forward with an
  additive migration; don't drop/recreate tables that might hold real user progress or issued
  certificates.
